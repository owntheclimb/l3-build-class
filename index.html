Ship Real Software

Today runs on seven prompts, pasted in order. You copy each one, paste it, and watch Claude do the engineering, and at two big moments the room decides together when to move. The panel beside each prompt explains how it was built, so after class you can write prompts like these for your own projects.

Get set up (three minutes, follow exactly)

  1. Log into your playground (the virtual computer) the same way you did last session. If you cannot get in, tell the instructor right away and watch the shared screen while it gets sorted; getting you in is the instructor's job. (If your setup runs directly on your own work computer instead of a remote playground, simply skip this step; everything else today is identical.)
  2. Inside the playground, open the Herd app (Start menu, type Herd) and wait until its services show green. Herd is the engine that serves your app; playgrounds that restarted turned it off, and without it your app page says "can't reach this page".
  3. Now open the Claude app. At the top left, click Code.
  4. Next to the word projects click the + sign. A folder window opens. Go to your Herd folder and pick the folder named playground-l3-yourname (the one with YOUR name; the letter after playground is a lowercase L). Click Select Folder.
CHECK: the top of the window now shows playground-l3-yourname. If it shows anything else, or you cannot find the folder, tell the instructor now, before pasting anything. A couple of setups from last session still need a two-minute finish, and that is completely expected.
CHECK: at the bottom right of the message box it should say Opus. If it says something else, click it and choose Opus.
  1. If Claude asks permission to read or edit files in this folder, say yes. If a Windows admin box ever pops up asking to make changes to the computer, the answer is No.
  2. One prompt at a time, in order, and let Claude finish before you paste the next one. You never need to type your own words into the chat today; every word you send lives in a copy box on this page. While Claude works, read what it says out loud in your head; that running commentary is half the class.
  3. If a sign-in window pops up inside the playground at any point, click your own account, let it finish, and come back. That is normal and it will happen at least once.
PROMPT 1

Meet Your Codebase

Watch and learn
Recon
WHY WE ARE HERE: I am in a live training class. Today you and I take one small feature from idea to a real pull request on this company's actual platform, the same way its engineers do. You do the engineering; I steer and decide. This prompt is step one: understand the ground before touching it. THINGS ABOUT THIS ENVIRONMENT YOU SHOULD KNOW ALL SESSION (so you can diagnose instead of guess): this is a Windows playground machine; the shell is Windows PowerShell 5 where && does not work, one command per line. The local site runs on http, not https; if https fails that is normal, use http. If the local site says "refused to connect" or "can't reach this page", the Herd services are not running: tell me to open the Herd app and wait for green, then continue where we left off. The app's Sign in button goes to company single sign-on that is known to be under repair; NEVER build anything that depends on logging in, and if a page redirects to a login error, that is the known issue, say so calmly. The database is remote and company-managed; if it is ever unreachable, report it plainly, do not try to install or start a database. Some repos contain leftover files from an earlier setup session; they are harmless, never delete them, never include them in commits. The code lives on the company's OWN Git server, reached with plain git and a browser sign-in; there is no GitHub here, so never suggest, install, or use GitHub tools or any other external code-hosting tool. When any command triggers a browser sign-in window, stop and hand it to me. If a Windows admin permission box appears, the answer is always No. YOU ARE: a senior Laravel engineer joining this codebase today. Read the repository and brief me in at most 14 SHORT lines, in plain language a non-engineer can follow: 1. What this app is built with and how I can see it in my browser. 2. What the company template already gives us for free: where login and security live (mark them OFF LIMITS, we never touch those), what built-in pages exist, where logs live. 3. Where things go when we build: routes, models, database migrations, pages, tests. Real folder paths from THIS repo. 4. The style rules this repo follows, including its typing standards, so everything we add matches. 5. The exact command this repo uses to run its own tests, found in its own files. 6. Which database this app talks to, name only, never any passwords or connection text. 7. Three things we should never touch in here, one plain reason each. 8. Housekeeping check, calmly: is this repo clean, or are there leftover files from earlier setup attempts (a starter-kit folder, extra notes files, anything uncommitted)? Just LIST what you find. Do not delete or move anything; we will simply build around it, and we will make sure none of it rides along when we submit our work later. RULES, for this prompt and every prompt today: read-only unless a prompt says otherwise; never print secrets; if something is unknowable say NOT FOUND instead of guessing. THE FIX-IT-YOURSELF RULE, standing all class: when something breaks or surprises you, you own it. Diagnose it with everything this briefing taught you about this environment, change your approach as many times as you need, quietly get us back on track, and then tell me in one line what happened and what you did. The only time you stop and hand me a sentence is when the fix needs a human: a sign-in window, a permission box, starting the Herd app, the network, or the instructor. In that case give me ONE plain sentence to relay or act on, and if the fix is a simple click or a single command, walk me through it in baby steps. Never sit in a silent retry loop repeating the same failing command; change the angle instead. THE CHECKPOINT RULE, standing all class: every new prompt I paste assumes the previous step ended well. If it did not, or if anything was left half-finished, your first job is to quietly finish or repair the previous step, tell me in one line what you fixed, and then do the new prompt. End your reply with the single line: Ready for Prompt 2.
What you doPaste the prompt, press Enter, and just read. When Claude ends with "Ready for Prompt 2," copy the next prompt.

How this prompt is built

  • "WHY WE ARE HERE..."Every strong prompt opens with context. When Claude knows what is happening, why it matters, and what a good outcome looks like, it makes better decisions for the whole session.
  • "YOU ARE: a senior Laravel engineer"Giving the AI a role tells it which habits to use. A senior engineer reads the code before changing anything and respects the rules of the house, so that is who we ask Claude to be.
  • "at most 14 SHORT lines... plain language"A limit keeps the answer readable. Without one, you would get a wall of text that nobody in the room has time to read.
  • "mark them OFF LIMITS"You set the boundaries before any work exists, and Claude carries those boundaries for the rest of the session.
  • "say NOT FOUND instead of guessing"This is the honesty rule. An AI that is allowed to say it does not know stops inventing answers.
  • "THE FIX-IT-YOURSELF RULE"When something breaks, Claude diagnoses it and repairs it on its own, using everything this briefing taught it about the machine it is standing on. It only hands you a sentence when the fix truly needs a human, like a sign-in window or the instructor.
  • "THE CHECKPOINT RULE"Every prompt you paste quietly finishes or repairs whatever the last step left behind before starting its own work. This is how the whole room ends up in the same place, even when different machines take different little detours.
PROMPT 2

The Plan: My Work Portal

Your first decision
Plan first, build later
Today we build MY WORK PORTAL: a personal task board that lives in this app FOR REAL. The tasks sit in the database, the page talks to a real API, and everything you change is still there after a refresh. That difference, a page backed by a server, is the whole point of today. PLAN ONLY. Do not create or change any file yet. The feature, exactly: - Database table portal_tasks (that exact name, chosen so we collide with nothing): id, title (text max 120), category (short word), status (waiting, doing, or done; default waiting), status_since (date), owner (a first name), due (date, optional), priority (1 to 3, default 2), notes (longer text, optional), timestamps. - The PortalTask model and a factory. - A seeder adding 8 realistic SAMPLE tasks for an operations person, invented names only, a mix of statuses, dues, and priorities, wired into this repo's normal seeding. - The API, placed in this repo's stateless api routes so the page's JavaScript can call it without the login system: GET /api/portal-tasks (all tasks, newest first), POST /api/portal-tasks (create with title, category, optional due and priority), PATCH /api/portal-tasks/{id} (update status, due, or notes; when status changes, set status_since to today). - A page at /my-portal: ONE standalone full page that does NOT extend the app's layout; all styles and script inline; no packages, no build step, no external files. The look, exactly: warm ivory background (#FAF7F2); one huge serif number at the top showing how many tasks are not done, with a small-caps label under it; three columns titled Waiting, Doing, Done; white cards with soft shadows showing title, category as a small tinted chip, owner, due date (amber when overdue), priority as one to three small dots; an add box at the top (title + category, Enter adds it as waiting through the API); clicking a card's circle marks it done through the API (strikethrough, moves to Done); a Defer button on non-done cards pushes due to tomorrow through the API. Every change saves through the API, so a refresh brings back exactly what you left. - Feature tests covering the three endpoints and the page. Also confirm in the plan, from your recon: that /my-portal and /api/portal-tasks are unused in this repo, and how this repo's api routes handle requests so our page's calls work without logging in (nothing we build may depend on login). Give me the plan in exactly this shape, short lines, plain words: FILES I WILL CREATE, one line each on what it is for. FILES I WILL TOUCH, one line each on the single line I am adding and why. TESTS I WILL WRITE, named, one line each on what it proves. RISKS, the 2 or 3 most likely ways this goes wrong in THIS repo. OUT OF SCOPE, always: login and security files, pipeline files, other tables, installing anything new, and any leftover setup files from earlier sessions (they stay exactly where they are, untouched). Then STOP and wait. Do not build anything until my next message begins with the word: approved. That message will also carry the build instructions.
What you doRead the plan like a boss reading a proposal. If it matches what we said, copy Prompt 3, your approval rides on its first word. If something looks off, raise your hand.

How this prompt is built

  • "PLAN ONLY. Do not create or change"This is the biggest quality trick in AI coding: make the AI think before it types. A mistake in a plan costs nothing to fix, while a mistake in code can cost the whole afternoon.
  • "The feature, exactly:"We spell out the exact shape of the feature so that everyone in the room builds the same thing. A vague wish would produce fifteen different apps.
  • "in exactly this shape"A structured plan can be checked in about a minute. When a plan is one long paragraph, the missing pieces hide inside it.
  • "OUT OF SCOPE, always"Writing down what we will not touch protects us far better than hoping the AI stays away from it on its own.
  • "until my next message begins with: approved"The word approved works like a password for permission, and it keeps you the decision-maker. The password sits on the first line of Prompt 3, so pasting the next prompt is how you say yes.
PROMPT 3

The Build

Claude works, you watch
Execute the plan
approved. Build EXACTLY the plan you just showed me, nothing extra. While you build: - Match this repo's own style and typing standards from your Prompt 1 briefing; when unsure, copy the pattern of the nearest existing example in this repo. - After each file, one plain line: what you made and what it is for. - Sample data and invented names only. Nothing outside this repo folder. Nothing new installed. Login, security, and pipeline files stay untouched. - If any write from the page comes back blocked (a 419 or 401 style refusal), that is the repo's request protection: use this repo's own pattern for page-to-API calls (its stateless api routes, or its token header) and tell me plainly which one you used and why. - If reality does not quite match the plan in some small way, adapt, stay inside the plan's boundaries, and tell me in one line what you changed and why. Only if the plan truly cannot work as approved do you stop and tell me in plain words what you found and what you suggest. The standing rules from Prompt 1 apply. When the code is written: run the database migration, run the seeder, and PROVE it, labeling every claim honestly: WORKS means you ran it and saw it; CHECKED THE CODE means you read it but did not run it; NOT TESTED means exactly that. Show me: the routes exist, a call to GET /api/portal-tasks with a piece of the JSON that came back, and a task CREATED through the API with its response. Then end with, exactly: YOUR TURN: open the browser INSIDE the playground (Edge on the playground desktop) and go to http://playground-l3-YOURNAME.test/my-portal. Add a task in the page (make it a FUN, made-up one, never a real work item; this is a demo database). Mark one done. Now REFRESH the page and watch everything stay. Replace YOURNAME with the real folder name so I can click it. Then: Ready for Prompt 4.
What you doWatch the build happen. When Claude says YOUR TURN, open the link it gives you in the playground browser and look at your own page, live. Then come back and copy Prompt 4.

How this prompt is built

  • "approved. Build EXACTLY the plan"The first word is the password from Prompt 2, so pasting this prompt is what opens the gate. The word EXACTLY matters just as much, because most bugs are born when a build quietly drifts away from its plan.
  • "copy the pattern of the nearest existing example"The codebase itself is the best style guide we have. This one line keeps the new code looking like it has always belonged here.
  • "WORKS / CHECKED THE CODE / NOT TESTED"These are the honesty labels. When an AI tells you something works, that means very little until you know whether it actually ran the code or only wrote it.
  • "showing me a piece of the JSON"We ask for real data on the screen because evidence is worth more than confidence.
  • "YOUR TURN: open your browser"You are the quality department today. The moment you see your own page in your own browser, this class stops being theory.
PROMPT 4

The Tests

The gate is real
Earn the pipeline's respect
Here is a fact about this company's platform: when code is submitted, an automatic pipeline runs the tests and REFUSES code that is not properly covered by them. Tests are not homework here; they are the toll gate. So: Write tests, using this repo's own testing style and tools, that prove: 1. GET /api/portal-tasks answers correctly with our seeded tasks, newest first. 2. POST creates a task that then appears in the list, and PATCH really changes status (and sets status_since to today). 3. The /my-portal page loads and shows a seeded task's title. And because happy tests lie, add EVIL TWINS: GET with a completely EMPTY table (still answers politely with an empty list, no crash); a title at exactly the 120 length limit; a PATCH aimed at a task id that does not exist (a polite not-found, never a crash); and a request using a method the routes should refuse. Then run this repo's FULL test suite, ours and everyone's, with the repo's own test command. Report plainly: how many passed, how many failed, how long it took. If anything fails, fix OUR code or OUR tests and run again until green, telling me each fix in one line. Never weaken or delete an existing test to get green; if an old test fails for reasons unrelated to us, label it PRE-EXISTING, leave it alone, and move on. The standing rules from Prompt 1 apply. End with: Ready for Prompt 5.
What you doWatch the test numbers climb toward green. Claude fixes its own failures along the way, and if a fix ever truly needs a human, it will hand you one plain sentence for the instructor.

How this prompt is built

  • "the pipeline... REFUSES code"We tell Claude what happens to weak work here: the company pipeline refuses code that is not tested well enough. Knowing a machine will judge the tests makes Claude write better ones.
  • "this repo's own testing style and tools"Generic tests might not even run in this codebase, so we ask Claude to use the testing tools this repo already uses on itself.
  • "EVIL TWIN"Every test that proves the feature works gets a twin that tries to break it: an empty list, a title at the exact length limit, a request through the wrong door. Real bugs live in those corners.
  • "run this repo's FULL test suite"Your feature passing its own tests means little if it quietly broke something next to it. Running the whole suite proves the rest of the codebase still works too.
  • "Never weaken or delete an existing test"Deleting a failing test is the most tempting shortcut an AI can take, so we ban it by name, out loud.
PROMPT 5

The Anti-Prompt

The signature move
Part one, the brutal audit
Change hats completely. You are now a brutal principal engineer reviewing this feature before it may ship, and your reputation depends on catching what is wrong with it. Audit ONLY what we built today. Score it 0 to 100, starting at 0, giving points only for what is proven solid. Hunt, in this order: real bugs (wrong data, wrong order, missed edge cases); places where our code does not match this repo's own style and typing standards; data safety (anything that looks like real names or company data, anything touching tables that are not ours); test gaps (what could break tomorrow with no alarm ringing); and the page itself (anything sloppy). RULES: LIST ONLY, no fixing. Numbered findings, most serious first, one plain-language line each on WHY it matters. No compliments, no filler. A clean category gets the single word CLEAN. Then STOP and wait. Do not fix anything until my next message.
Part two, paste after the room hears the results
Fix the TWO most dangerous findings from your own list. Tell me in one plain line each which two you chose and why. Fix exactly those two, nothing else. Rerun the full test suite, show it green, and label every other finding KNOWN, NOT FIXED, which is the honest way professionals ship. End with: Ready for Prompt 6.
What you doRead the list while the instructor walks one audit out loud for the room. Then paste part two and watch Claude repair the two most dangerous things on its own list.

How this prompt is built

  • "Change hats completely"The brain that built something will defend it. Giving Claude a completely new role with the opposite goal is how you find what the builder skipped. This is the anti-prompt, and it may be the most useful prompt you learn today.
  • "starting at 0"Starting the score at zero changes the psychology. The reviewer has to find reasons to award points instead of finding excuses to wave the work through.
  • "LIST ONLY, no fixing"Finding problems and fixing problems are kept as two separate steps, because doing both in one breath turns into chaos.
  • "the TWO most dangerous findings"A small, bounded fix can be checked properly. An open instruction to fix everything at once is how working software gets wrecked an hour before a deadline.
  • "KNOWN, NOT FIXED"Real teams ship with an honest list of what they chose not to fix today, written down where everyone can see it.
PROMPT 6

The Pull Request

The robots review you
Submit it for real
Time to submit our work the way this company's engineers do, so the platform itself can judge it. Step by step, telling me each result in plain words: 1. Make a branch named feat/work-portal-MYNAME (use the name from this repo's folder). 2. Before committing, list BY NAME exactly which files you are about to include; they must be only the files from our approved plan. NEVER sweep everything in; if the repo shows other changed or leftover files, they stay out, no exceptions. Then make one commit of our feature, written in the same style as this repo's existing commit messages (look at a few first). 3. Push the branch. A browser sign-in may appear on my screen; tell me to complete it and WAIT for me. Never let a command sit waiting silently. 4. Open a pull request into the qa branch on the company Git server. Do not install or reach for any extra tool for this; if you have no way to open it yourself, that is completely fine and expected: give me the exact link to click and tell me precisely what to press, in baby steps. The PR description is five short lines: WHAT we added, WHY, HOW IT IS TESTED, RISK, and ROLLBACK (undoing this one commit). In the RISK line, state plainly: sample data only, nothing sensitive; the page and endpoints are public on purpose for this exercise, and they move behind company sign-in once the hub login fix lands. Saying it in the PR turns a reviewer question into proof we thought it through. 5. Now the moment of truth. We wait and watch the PR page together. Tell me what to look for, and as results come in, report: did the test pipeline run, what did the coverage check decide, and did the automated reviewer leave a review? Quote what the robot reviewer says and translate every finding into plain English for me. DO NOT MERGE ANYTHING. The merge is a decision the whole class makes together with the instructor. If the pipeline or the reviewer rejects us, say so calmly and plainly: a rejection is the platform doing its job, and fixing one finding is Prompt 7. The standing rules from Prompt 1 apply.
What you doComplete the sign-in if it pops. Click the link it gives you and press the green button it names. Then watch the checks appear on the PR page, live. This is your code being judged by the company's real machinery.

How this prompt is built

  • "the way this company's engineers do"At this point the class stops being an exercise. Your work goes through the same branches, the same pipeline, and the same robot reviewer that this company's engineers face every day.
  • "tell me to complete it and WAIT for me"Sign-in windows belong to humans. Claude is taught to hand them to you and wait, which prevents the silent hang, the single most confusing failure a beginner can hit.
  • "five short lines: WHAT, WHY, HOW TESTED, RISK, ROLLBACK"This five-line description is what makes a reviewer trust a submission. Thinking about how you would undo a change before you merge it is a habit of senior engineers.
  • "translate every finding into plain English"Robot reviews arrive written for engineers. Asking Claude to translate each finding into plain English means you can read them without fear.
  • "DO NOT MERGE ANYTHING"Merging changes the shared codebase that everyone works in, so that decision stays with humans. Today the whole class makes it together.
PROMPT 7

The Landing

Together, on the instructor's go
Close the loop
Final stretch, and we do it like professionals: 1. If the pipeline or the robot reviewer raised findings on our PR: pick the SINGLE smallest real one, tell me what it means in one plain sentence, fix exactly that, rerun the full test suite green, and push again to the same branch. If everything came back clean, say so and skip to step 2. 2. HOLD. Do not merge until my next message begins with the word: land. That word comes from the instructor for the whole class together. 3. After I say land: merge the pull request into qa exactly the way this repo expects, no force, and then tell me in plain words where I can watch the deployment happen and what I should expect to see when my feature is live in the QA environment. If nothing appears, report what you can see and stop; no retries, no side doors. 4. Close out with five honest lines: what we shipped, what is proven WORKING, what is KNOWN NOT FIXED, what we would do first next session, and one thing about this codebase worth remembering. Then end with this, word for word: You just read a real codebase, planned a feature, built it, tested it, survived a brutal audit, and shipped it through the same pipeline the engineering team uses. That is vibe coding done like an engineer. Keep the loop; change the feature.
The landing word, paste only when the instructor calls it
land. Go ahead with steps 3 and 4 now.
What you doWait for the instructor to call it, then paste the landing word above. Watch your feature deploy. That screen is worth a photo.

How this prompt is built

  • "the SINGLE smallest real one"Fixing things at the last minute is the riskiest moment in shipping software. Choosing the single smallest real finding keeps the risk tiny and the lesson intact.
  • "until my next message begins with: land"This is the second password of the day, and it gets pasted from its own box rather than typed from memory. An action you cannot undo deserves an explicit human word, every single time.
  • "where I can watch the deployment"A good deploy is boring and visible. Watching your own commit appear in a real company environment is the payoff of the whole class.
  • "no retries, no side doors"When shipping misbehaves, a professional stops, observes, and reports what happened. We do not let Claude keep pushing buttons and hoping.
  • "five honest lines"Every real ship ends with a truthful summary, including what is not done yet. That honest list is what makes the next session easy to start.

Homework: Make It Beautiful, Ship It Again

The repeat rep
Round two, solo: part one, the plan
Homework round, same rules as class. Look at The App tab on the class page: that is the full vision this portal grows into. Pick exactly ONE piece of it: the living sky header, an Urgent tab, or a Week strip. PLAN ONLY first: what you will add to /my-portal, which files you will touch, which tests you will add, changing NOTHING about the existing endpoints or any other page. Then STOP and wait. Do not build until my next message begins with the word: approved.
Part two, paste when the plan looks right
approved. Build it: keep every test green, run the full suite, then ship it EXACTLY like class: new branch feat/portal-upgrade-MYNAME, one commit of only the planned files, push (hand me the sign-in), pull request into qa with the five-line description, then read me the robot review in plain English. Do not merge; the instructor looks first. The point of this round: you just ran the whole loop yourself. That is the skill.
What you doThis one is yours alone, after class or when the instructor says there is time. Same rhythm: read the plan, and when it looks right paste part two, your approval rides on its first word. Complete the sign-in, click the PR link, read the review.

Why homework is a second PR

  • "same rules as class"The loop itself is the lesson. Running it a second time, on your own, on a feature you chose, is what makes it stick.
  • "changing NOTHING about the data"A purely visual change with green tests is the safest possible second round, and it still walks through every gate the class walked through.
  • "a page a manager would screenshot"Beauty counts as a requirement too. When you name the standard you want out loud, the AI rises to meet it.

If anything feels stuck

  • Start by looking for a hidden permission box or a browser sign-in window hiding behind your other windows; those wait quietly for you. And a few quiet minutes usually just means Claude is thinking.
  • If Claude really does seem stuck, paste this: "Stop. In five plain lines: what were you doing, what exactly went wrong (quote the error), what did you already try, what do you need from me, and what should I tell the instructor? If you can still fix this yourself with everything you know about this machine, say so and go ahead."
  • Then raise your hand with that answer on your screen, and the instructor takes it from there.
