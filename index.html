Level 3 · Session 3

Ship Real Software

Seven prompts, run in order, on your own playground repo. By the end you will have taken a feature through the full professional loop: read the codebase, plan, build, test, audit, open a pull request, and watch the company pipeline judge your work. The panel beside each prompt explains WHY it is written the way it is; that anatomy is the real lesson.

Before Prompt 1 (two minutes)

  1. Open a terminal on your playground machine and go to YOUR repo folder: cd $HOME\Herd\playground-l3-<yourname> (one command per line in this shell; no && chaining).
  2. Start Claude Code with claude from INSIDE that folder. The folder you start in is the project root; wrong root means blocked file tools.
  3. When installs or edits ask for permission inside this repo, accept them; this is your sandbox. Anything asking to touch files OUTSIDE the repo, or any Windows admin prompt: the answer is No.
  4. One task at a time. While Claude works, watch it work; read what it says it is doing. That narration is half the class.
  5. If a git command triggers a browser sign-in, complete it in the browser and come back. Never let a terminal sit on a hidden prompt.
PROMPT 1

Read the Codebase

Unskippable
Recon
You are a senior Laravel engineer joining this codebase today. Before writing anything, read the repository and give me a briefing of at most 14 lines: 1. Framework and version, and how this app is served locally. 2. What the company template gives us for free: where authentication and SSO are wired (mark them OFF LIMITS, we never touch them), what built-in pages or dashboards exist, where application logs live. 3. Where things go: routes, controllers or actions, models, migrations, views or pages, tests. One line each, with real paths from THIS repo. 4. The conventions you observed: naming style, how existing migrations and tests are written, anything a new engineer must imitate. 5. The exact command this repo uses to run its test suite, found from its own files, not guessed. 6. Which database engine this app talks to, by NAME ONLY from config; never print credentials or connection strings. 7. Three things a new engineer should NOT touch in this repo, with one reason each. Rules: read only, change nothing, install nothing. If something is unknowable from the repo, say NOT FOUND rather than guessing. End with: WHAT YOU DO NOW: one line telling me to read your briefing out loud to myself, then paste PROMPT 2.

Why this prompt is built this way

  • "You are a senior Laravel engineer joining..."Role framing is not decoration. It selects which patterns the model reaches for: a "senior engineer" reads before writing and respects conventions; an unframed model starts inventing.
  • "at most 14 lines"A hard cap forces prioritization. Unbounded summaries bury the load-bearing facts in filler.
  • "mark them OFF LIMITS"You declare the blast radius BEFORE any work exists. The AI now carries that boundary through the whole session.
  • "with real paths from THIS repo"Anchoring every claim to a path makes hallucination visible: a fake path fails the moment you look.
  • "found from its own files, not guessed"Models trained on the whole internet will happily give you the GENERIC Laravel answer. You want THIS repo's answer.
  • "say NOT FOUND rather than guessing"You are teaching the honesty contract early. It pays off in every later prompt.
PROMPT 2

Plan Before Code

Unskippable
The Feature Plan
We are building one small real feature: a SUGGESTION BOX for shop-floor and office improvement ideas. PLAN ONLY in this step. Do not create or modify any file yet. The feature, exactly: - One migration creating a suggestions table: id, title (string, max 120), details (text, nullable), submitted_by (string, a person's name), status (string, default "new"), timestamps. - One model with a factory. - One seeder inserting five realistic SAMPLE suggestions with fictional names only; wire it so the repo's normal seed command runs it. - One JSON endpoint: GET /api/suggestions returning all suggestions newest first. - One simple page at /suggestions listing them in a clean table: title, submitted by, status, date. Follow this repo's existing page and styling conventions from your Prompt 1 recon; do not invent a new design system. - Feature tests covering the endpoint and the page. Your plan, in this exact structure, then STOP and WAIT for my approval: FILES I WILL CREATE: each with a one-line purpose. FILES I WILL TOUCH: each with the one line I am adding and why (routes files count). TESTS I WILL WRITE: named, one line each on what they prove. RISKS: the 2 or 3 most likely ways this goes wrong in THIS repo. OUT OF SCOPE: authentication, SSO, CI and pipeline files, other tables, new composer or npm packages. If the plan seems to need a new package, flag it as a risk instead of adding it. Do not begin building until I reply with the word: approved.

Why this prompt is built this way

  • "PLAN ONLY... Do not create or modify"The single biggest quality lever in AI coding. A model that plans first exposes its misunderstandings while they are still free to fix.
  • "The feature, exactly:"We hand it the exact schema so every seat in the room converges on the same product. Vague specs are why two people who "built the same thing" have nothing in common.
  • "in this exact structure"A structured plan is reviewable in 60 seconds. Prose plans hide missing pieces.
  • "FILES I WILL TOUCH"The touch list is your diff preview. Anything not on it later is scope drift, and you get to call it out.
  • "OUT OF SCOPE:"Naming what we will NOT do is stronger than hoping. Especially: no new packages on a company machine.
  • "until I reply with the word: approved"A literal approval token. You stay the engineer; the AI stays the brilliant intern.
PROMPT 3

Build It

Unskippable
Execute the Plan
approved. Build EXACTLY the approved plan, nothing more. Rules while you build: - Follow the conventions you reported in your recon; when in doubt, imitate the nearest existing example in this repo. - After each file you create or touch, one line: the path and what it is for. - Sample data only, fictional names only, no real company data ever. - Nothing outside this repo; no new packages; auth, SSO, CI, and pipeline files stay untouched. - If something in the plan turns out to be wrong for this repo, STOP and tell me what you found and what you recommend instead. Do not silently improvise. When the code is written: run the migration, run the seeder, then prove it with evidence, labeling every claim honestly: WORKS means you executed it and observed the result; STATICALLY VERIFIED means you read the code but did not run it; NOT TESTED means exactly that. Show me: the migration run output, the seeder run output, the route list entry for /api/suggestions and /suggestions, and a curl of the API endpoint with the JSON it returned. End with: WHAT YOU DO NOW: tell me to open the /suggestions page in my browser myself and look at it with my own eyes, then come back and paste PROMPT 4.

Why this prompt is built this way

  • "approved. Build EXACTLY the approved plan"The approval token opens the gate, and "exactly" closes the side doors. Drift between plan and build is where bugs breed.
  • "imitate the nearest existing example"The best convention document is the codebase itself. This one line prevents a foreign-looking feature.
  • "STOP and tell me what you found"Plans meet reality. You want a report, not a silent workaround you discover three prompts later.
  • "labeling every claim honestly: WORKS..."The three-label honesty system. "It works" from an AI means nothing until you know whether it RAN it or just wrote it.
  • "a curl of the API endpoint"Evidence, not confidence. JSON on the screen is proof; "the endpoint should work" is not.
  • "open the page... with my own eyes"You are the QA department. The browser check belongs to a human, always.
PROMPT 4

Tests, or the Pipeline Says No

Unskippable
Earn the Gate
This company's pipeline rejects pull requests that are not covered by tests. Your job now: make our feature genuinely covered, using this repo's own test tooling and the exact test command you found in recon. Write feature tests that prove: 1. GET /api/suggestions returns 200, JSON, and the seeded suggestions newest first. 2. The /suggestions page renders and shows a seeded suggestion's title. 3. The model factory produces valid records. And one EVIL TWIN for each happy path, because happy paths lie: the endpoint with an EMPTY suggestions table (still 200, empty list, no crash); a title at exactly the 120-character boundary; and a request to the endpoint with a method it should not accept. Then run the FULL test suite, not just our new tests, and report: total passing, total failing, wall time, and whether our new files are covered by the tests you wrote (show which test hits which file). If anything fails, fix our feature code or our tests until the suite is green, narrating each fix in one line. Never weaken or delete an existing test to get to green; if an existing test fails for reasons unrelated to us, report it as PRE-EXISTING and leave it. Labels as always: WORKS, STATICALLY VERIFIED, or NOT TESTED. End with: WHAT YOU DO NOW: paste PROMPT 5.

Why this prompt is built this way

  • "the pipeline rejects pull requests"Tests here are not homework; they are the toll gate. The company enforces coverage on both ends of the stack. This is why professionals test: the machine says no otherwise.
  • "this repo's own test tooling"Generic test advice produces tests the pipeline does not even run. The repo defines the game.
  • "one EVIL TWIN for each happy path"Every test that proves it works has a sibling that tries to break it. Empty states, boundaries, wrong methods: that is where real bugs live.
  • "run the FULL test suite"Your feature passing means little if you broke someone else's. The suite is the contract with the whole codebase.
  • "Never weaken or delete an existing test"The most tempting AI shortcut in existence, banned by name.
  • "report it as PRE-EXISTING and leave it"Honesty over heroics; scope discipline even in repair.
PROMPT 5

The Anti-Prompt

The Signature Move
Brutal Audit, List Only
Now become a different person: a brutal principal engineer reviewing this feature before it may ship, whose reputation depends on finding what is wrong. Audit ONLY what we built this session. Score it 0 to 100, starting from 0, awarding points only for what is verifiably solid. Hunt in this order: correctness bugs (wrong data, wrong order, edge cases we missed); convention violations against this repo's own patterns; data safety (any real-looking data, anything touching tables that are not ours, any secret in code or output); test gaps (what could break tomorrow that no test would catch); and the page itself (would an engineer be embarrassed by this table's markup or naming). RULES: LIST ONLY. Do not fix anything. Number every finding, one line of WHY it matters each, most severe first. No praise, no filler. If you find nothing in a category, say CLEAN and move on. When the list is done, STOP and ask me to pick which findings to fix. I will pick at most three. Then fix EXACTLY those, most severe first, rerun the full test suite, and show it green. Touch nothing else, including findings I did not pick: report those as KNOWN, NOT FIXED. End with: WHAT YOU DO NOW: paste PROMPT 6.

Why this prompt is built this way

  • "become a different person"The same model that built the code will defend it. A new role with opposite incentives finds what the builder-brain skips. This is the anti-prompt: the most important prompt you will ever learn.
  • "Score it 0 to 100, starting from 0"Starting from zero flips the grading psychology from "find reasons to pass" to "find reasons to award."
  • "LIST ONLY. Do not fix anything."Finding and fixing in one breath explodes scope and buries the list. Separate the audit from the surgery.
  • "I will pick at most three"Bounded fixes are verifiable fixes. Unbounded fixing is how a working feature dies at 10:55.
  • "report those as KNOWN, NOT FIXED"An honest known-issues list beats silent perfection claims. This is what real engineering teams ship with.
PROMPT 6

Open the Pull Request

The Real World
Ship It to the Robots
Time to ship the way this company ships. Steps, in order, reporting each result verbatim: 1. Create a branch named feat/suggestion-box-<my initials> from the current branch. 2. One commit containing our feature, message in this repo's own commit style (check the log first and imitate it). 3. Push the branch. If a browser sign-in appears, hand it to me and wait. 4. Open a pull request into the qa branch. If you have no tool for that, give me the exact URL to open and tell me precisely what to click. The PR description is five short lines: WHAT it adds, WHY, HOW IT IS TESTED, RISK, ROLLBACK (reverting this one commit). 5. Then we WAIT and watch, and this is the lesson: report what the pipeline does with our PR. Does a test run start? Does a coverage check appear, and what number does it report? Does the automated reviewer leave a review, and what does it say? Quote its findings verbatim and translate each one into plain English for me. DO NOT MERGE. Merging is a decision we make together in class after reading the robot's review. If the pipeline rejects us, that is not failure, that is the system working; report the reason and we will fix it together. End with: WHAT YOU DO NOW: watch the pull request page with me until the checks finish, then we read the review out loud together.

Why this prompt is built this way

  • "the way this company ships"This is the moment the class stops being an exercise. Same branch flow, same pipeline, same robot reviewer your colleagues face every day.
  • "imitate it" (the commit style)Commit history is a public record. Matching its style is the difference between a teammate and a tourist.
  • "five short lines: WHAT, WHY, HOW TESTED, RISK, ROLLBACK"The PR description template that makes reviewers trust you. Rollback thinking before merge is a senior habit.
  • "report what the pipeline does"Coverage gates and AI reviewers judge your code within minutes. Learning to READ their feedback calmly is the actual skill.
  • "DO NOT MERGE"Merge is a human decision with blast radius. The robots advise; people decide.
  • "that is the system working"Reframing rejection as protection. The gate exists to catch us, and sometimes it will.
PROMPT 7

Land It

Together, On the Trainer's Go
Close the Loop
We read the review together. Now finish like a professional: 1. If the automated review or the pipeline raised findings on our PR: pick the SINGLE smallest real one, fix exactly it, rerun the full test suite green, push the same branch, and confirm the checks rerun. If everything came back clean, say so and skip to step 2. 2. HOLD until I say the word: land. Only then merge the pull request into qa, without force, exactly as this repo's flow expects. 3. After the merge: tell me where to watch the deployment land in the company portal, and what I should expect to see when it is live in the QA environment. If a deploy does not appear, report what you can observe and stop; no retries, no side doors. 4. Then the honest close-out, five lines: what we shipped, what is verified WORKING in QA, what is KNOWN NOT FIXED from the audit, what a next session would do first, and the one thing about this codebase a teammate should learn from our PR. End with: WHAT YOU DO NOW: a two-line recap I can say out loud: today you read a codebase, planned, built, tested, survived a brutal audit, and shipped a feature through the same pipeline the engineering team uses. That is vibe coding done like an engineer. Keep the loop; change the feature.

Why this prompt is built this way

  • "pick the SINGLE smallest real one"Last-minute fixes are where working features die. Smallest-real keeps the risk tiny and the lesson intact.
  • "HOLD until I say the word: land"The second literal token of the day. Irreversible actions get explicit human words, never implied consent.
  • "tell me where to watch the deployment"Deploys should be boring and observable. Watching your commit surface in a real environment is the payoff moment of the whole class.
  • "no retries, no side doors"When shipping misbehaves, professionals observe and report; they do not jiggle the handle harder.
  • "the honest close-out, five lines"Every real ship ends with a truthful summary including what is NOT done. Confidence without a gaps list is how trust dies.

If you get stuck (the unstick prompt)

  • First: is there an approval dialog hiding somewhere, or a browser sign-in waiting? Three quiet minutes is not stuck.
  • If truly stuck, paste this: "Stop. In five lines: what were you doing, what is the exact error verbatim, what have you tried, what do you need from me, and what is the smallest safe next step? Do not retry anything until I answer."
  • Console errors from the browser: right-click the page, Inspect, Console tab, copy the red text, paste it to Claude with the words "this is the browser console error."
