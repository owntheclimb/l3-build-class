Ship Real Software

Seven prompts, in order. You copy, you paste, you watch, and you make the two decisions only a human gets to make. Claude does the engineering; the prompts do the teaching; the panel next to each prompt shows you how it was built so you can build your own.

Get set up (three minutes, follow exactly)

  1. Log into your playground (the virtual computer) the same way you did last session. Cannot get in? Raise it now; that is an instructor item, not a you problem.
  2. Inside the playground, open the Claude app. At the top left, click Code.
  3. Next to the word projects click the + sign. A folder window opens. Go to your Herd folder and pick the folder named playground-l3-yourname (the one with YOUR name; the letter after playground is a lowercase L). Click Select Folder.
CHECK: the top of the window now shows playground-l3-yourname. If it shows anything else, or you cannot find the folder, tell the instructor now, before pasting anything. A couple of setups from last session need a two-minute finish; that is expected, not falling behind.
CHECK: at the bottom right of the message box it should say Opus. If it says something else, click it and choose Opus.
  1. If Claude asks permission to read or edit files in this folder, say yes. If a Windows admin box ever pops up asking to make changes to the computer, the answer is No.
  2. One prompt at a time, in order, and let Claude finish before you type anything. While it works, read what it says out loud in your head; that running commentary is half the class.
  3. If a sign-in window pops up inside the playground at any point, click your own account, let it finish, and come back. That is normal and it will happen at least once.
PROMPT 1

Meet Your Codebase

Watch and learn
Recon
WHY WE ARE HERE: I am in a live training class. Today you and I take one small feature from idea to a real pull request on this company's actual platform, the same way its engineers do. You do the engineering; I steer and decide. This prompt is step one: understand the ground before touching it. YOU ARE: a senior Laravel engineer joining this codebase today. Read the repository and brief me in at most 14 SHORT lines, in plain language a non-engineer can follow: 1. What this app is built with and how I can see it in my browser. 2. What the company template already gives us for free: where login and security live (mark them OFF LIMITS, we never touch those), what built-in pages exist, where logs live. 3. Where things go when we build: routes, models, database migrations, pages, tests. Real folder paths from THIS repo. 4. The style rules this repo follows, including its typing standards, so everything we add matches. 5. The exact command this repo uses to run its own tests, found in its own files. 6. Which database this app talks to, name only, never any passwords or connection text. 7. Three things we should never touch in here, one plain reason each. 8. Housekeeping check, calmly: is this repo clean, or are there leftover files from earlier setup attempts (a starter-kit folder, extra notes files, anything uncommitted)? Just LIST what you find. Do not delete or move anything; we will simply build around it, and we will make sure none of it rides along when we submit our work later. RULES, for this prompt and every prompt today: read-only unless a prompt says otherwise; never print secrets; if something is unknowable say NOT FOUND instead of guessing. THE BLOCKER RULE, standing all class: if you hit a real problem you cannot solve yourself within two attempts, STOP, and give me ONE plain sentence to relay to the instructor, plus, if the fix is a simple click or a single command, walk me through it in baby steps. Never retry quietly in a loop. End your reply with the single line: Ready for Prompt 2.
What you doPaste, press Enter, and just read. When you see "Ready for Prompt 2," copy the next prompt.

How this prompt is built

  • "WHY WE ARE HERE..."Every strong prompt opens with context: what is happening, why, and what the outcome should be. Claude behaves differently when it knows the mission, not just the task.
  • "YOU ARE: a senior Laravel engineer"A role tells the AI which habits to use. A "senior engineer" reads before writing and respects rules; an unframed AI just starts typing code.
  • "at most 14 SHORT lines... plain language"Limits force clarity. Without a cap you get a wall of text nobody reads.
  • "mark them OFF LIMITS"You set boundaries BEFORE work exists, and the AI carries them the whole session.
  • "say NOT FOUND instead of guessing"The honesty rule. An AI that may say "I don't know" stops inventing.
  • "THE BLOCKER RULE"The escape hatch: rare, controlled, human-in-the-loop. This one paragraph is why today's class does not need 40 rescue missions.
PROMPT 2

The Plan

Your first decision
Plan first, build later
Today's feature is a SUGGESTION BOX: a place where anyone in the company could post an improvement idea, and everyone can see the list. Small on purpose; the way we build it is the lesson. PLAN ONLY. Do not create or change any file yet. The feature, exactly: - A suggestions table in the database: id, title (text, max 120), details (longer text, optional), submitted_by (a person's name), status (starts as "new"), timestamps. - The model and a factory for it. - A seeder that adds five realistic SAMPLE suggestions, invented names only, wired into this repo's normal seeding. - An API endpoint: GET /api/suggestions, returning every suggestion as JSON, newest first. - A page at /suggestions showing them in a clean simple table: title, who, status, date, styled the way THIS repo styles pages. IMPORTANT: both the page and the API must be viewable WITHOUT logging in. If this repo protects everything behind login by default, plan ours as public routes outside that protection; if that is truly impossible here, flag it as a risk instead of building a locked door. - Tests that prove the endpoint and the page work. Give me the plan in exactly this shape, short lines, plain words: FILES I WILL CREATE, one line each on what it is for. FILES I WILL TOUCH, one line each on the single line I am adding and why. TESTS I WILL WRITE, named, one line each on what it proves. RISKS, the 2 or 3 most likely ways this goes wrong in THIS repo. OUT OF SCOPE, always: login and security files, pipeline files, other tables, installing anything new, and any leftover setup files from earlier sessions (they stay exactly where they are, untouched). If the plan seems to need something new installed, list it as a risk instead. Then STOP and wait. Do not build anything until I reply with the single word: approved
What you doRead the plan like a boss reading a proposal. If it matches what we said, type: approved

How this prompt is built

  • "PLAN ONLY. Do not create or change"The single biggest quality trick in AI coding: make it think before it types. Mistakes in a plan cost nothing; mistakes in code cost the afternoon.
  • "The feature, exactly:"We spell out the exact shape so all fifteen of us build the same thing. Vague wishes produce fifteen different apps.
  • "in exactly this shape"A structured plan can be checked in 60 seconds. A paragraph hides missing pieces.
  • "OUT OF SCOPE, always"Saying what we will NOT do protects us better than hoping.
  • "until I reply with the single word: approved"A literal password for permission. You stay the decision-maker; the AI stays the brilliant builder.
PROMPT 3

The Build

Claude works, you watch
Execute the plan
Build EXACTLY the approved plan, nothing extra. While you build: - Match this repo's own style and typing standards from your Prompt 1 briefing; when unsure, copy the pattern of the nearest existing example in this repo. - After each file, one plain line: what you made and what it is for. - Sample data and invented names only. Nothing outside this repo folder. Nothing new installed. Login, security, and pipeline files stay untouched. - If the plan meets reality and something does not fit, STOP and tell me in plain words what you found and what you suggest. No silent improvising. The standing BLOCKER RULE applies. When the code is written: run the database migration, run the seeder, and PROVE it all works, labeling every claim honestly: WORKS means you ran it and saw it; CHECKED THE CODE means you read it but did not run it; NOT TESTED means exactly that. Show me the route exists and call the API yourself, showing me a piece of the JSON that came back. Then end with, exactly: YOUR TURN: open the browser INSIDE the playground (Edge on the playground desktop) and go to http://playground-l3-YOURNAME.test/suggestions, look at your new page, and come back. Replace YOURNAME with the real folder name so I can click it. Then: Ready for Prompt 4.
What you doWatch it build. When it says YOUR TURN, open the link it gives you in the playground browser and look at YOUR page, live. Then come back and copy Prompt 4.

How this prompt is built

  • "Build EXACTLY the approved plan"The approval opened the gate; "exactly" closes the side doors. Drift between plan and build is where bugs are born.
  • "copy the pattern of the nearest existing example"The codebase is the best style guide. This one line keeps new code looking like it belongs.
  • "WORKS / CHECKED THE CODE / NOT TESTED"The honesty labels. "It works" from an AI means nothing until you know whether it RAN it or just wrote it.
  • "showing me a piece of the JSON"Evidence beats confidence. Data on screen is proof.
  • "YOUR TURN: open your browser"The human is the QA department. Seeing YOUR page in YOUR browser is the moment this stops being theoretical.
PROMPT 4

The Tests

The gate is real
Earn the pipeline's respect
Here is a fact about this company's platform: when code is submitted, an automatic pipeline runs the tests and REFUSES code that is not properly covered by them. Tests are not homework here; they are the toll gate. So: Write tests, using this repo's own testing style and tools, that prove: 1. GET /api/suggestions answers correctly with our suggestions, newest first. 2. The /suggestions page loads and shows a seeded suggestion's title. 3. The factory produces valid records. And because happy tests lie, add one EVIL TWIN each: the endpoint with a completely EMPTY table (must still answer politely, not crash); a title at exactly the 120 length limit; and a request using a method the endpoint should refuse. Then run this repo's FULL test suite, ours and everyone's, with the repo's own test command. Report plainly: how many passed, how many failed, how long it took. If anything fails, fix OUR code or OUR tests and run again until green, telling me each fix in one line. Never weaken or delete an existing test to get green; if an old test fails for reasons unrelated to us, label it PRE-EXISTING, leave it alone, and move on. BLOCKER RULE stands. End with: Ready for Prompt 5.
What you doWatch the numbers. Green is the goal. If it gets stuck fixing the same thing over and over, the Blocker Rule will kick in and tell you what to say to the instructor.

How this prompt is built

  • "the pipeline... REFUSES code"We tell Claude the consequence, not just the task. It writes better tests when it knows a machine will judge them.
  • "this repo's own testing style and tools"Generic tests might not even run here. The repo defines the game.
  • "EVIL TWIN"Every test proving it works gets a sibling trying to break it. Empty lists, edge lengths, wrong doors: that is where real bugs hide.
  • "run this repo's FULL test suite"Your feature passing means little if you broke a neighbor. The full suite is the handshake with the whole codebase.
  • "Never weaken or delete an existing test"The most tempting AI shortcut in existence, banned by name, out loud.
PROMPT 5

The Anti-Prompt

The signature move
Brutal audit, then surgery
Change hats completely. You are now a brutal principal engineer reviewing this feature before it may ship, and your reputation depends on catching what is wrong with it. Audit ONLY what we built today. Score it 0 to 100, starting at 0, giving points only for what is proven solid. Hunt, in this order: real bugs (wrong data, wrong order, missed edge cases); places where our code does not match this repo's own style and typing standards; data safety (anything that looks like real names or company data, anything touching tables that are not ours); test gaps (what could break tomorrow with no alarm ringing); and the page itself (anything sloppy). RULES: LIST ONLY, no fixing. Numbered findings, most serious first, one plain-language line each on WHY it matters. No compliments, no filler. A clean category gets the single word CLEAN. Then STOP and ask me to choose. I will pick up to TWO findings by number. Fix exactly those, rerun the full test suite, show it green, and label everything else KNOWN, NOT FIXED, which is the honest way professionals ship. End with: Ready for Prompt 6.
What you doRead the list. Pick the two that scare you most and reply like: fix 1 and 3

How this prompt is built

  • "Change hats completely"The builder brain defends its own work. A new role with opposite incentives finds what the builder skipped. This is the anti-prompt, the most important prompt you will ever learn.
  • "starting at 0"Starting from zero flips the psychology: it must find reasons to award points, not excuses to pass you.
  • "LIST ONLY, no fixing"Finding and fixing in one breath turns into chaos. First the list, then the surgery, separately.
  • "I will pick up to TWO"Bounded fixes stay verifiable. Unbounded "fix everything" is how working software dies an hour before a deadline.
  • "KNOWN, NOT FIXED"Real teams ship with an honest list of what they chose not to fix today. Hiding it is the amateur move.
PROMPT 6

The Pull Request

The robots review you
Submit it for real
Time to submit our work the way this company's engineers do, so the platform itself can judge it. Step by step, telling me each result in plain words: 1. Make a branch named feat/suggestion-box-MYNAME (use the name from this repo's folder). 2. Before committing, list BY NAME exactly which files you are about to include; they must be only the files from our approved plan. NEVER sweep everything in; if the repo shows other changed or leftover files, they stay out, no exceptions. Then make one commit of our feature, written in the same style as this repo's existing commit messages (look at a few first). 3. Push the branch. A browser sign-in may appear on my screen; tell me to complete it and WAIT for me. Never let a command sit waiting silently. 4. Open a pull request into the qa branch. If you cannot open it yourself, give me the exact link to click and tell me precisely what to press, in baby steps. The PR description is five short lines: WHAT we added, WHY, HOW IT IS TESTED, RISK, and ROLLBACK (undoing this one commit). 5. Now the moment of truth. We wait and watch the PR page together. Tell me what to look for, and as results come in, report: did the test pipeline run, what did the coverage check decide, and did the automated reviewer leave a review? Quote what the robot reviewer says and translate every finding into plain English for me. DO NOT MERGE ANYTHING. The merge is a decision the whole class makes together with the instructor. If the pipeline or the reviewer rejects us, say so calmly and plainly: a rejection is the platform doing its job, and fixing one finding is Prompt 7. BLOCKER RULE stands.
What you doComplete the sign-in if it pops. Click the link it gives you and press the green button it names. Then watch the checks appear on the PR page, live. This is your code being judged by the company's real machinery.

How this prompt is built

  • "the way this company's engineers do"The class stops being an exercise here. Same branch, same pipeline, same robot reviewer your colleagues face daily.
  • "tell me to complete it and WAIT for me"Sign-ins belong to humans. Teaching the AI to hand them over prevents silent hangs, the most confusing failure a beginner can hit.
  • "five short lines: WHAT, WHY, HOW TESTED, RISK, ROLLBACK"The description template that makes reviewers trust a submission. Thinking about the undo BEFORE merging is a senior habit.
  • "translate every finding into plain English"Robot reviews arrive in engineer-speak. Making the AI translate them is how a vibe coder reads them without fear.
  • "DO NOT MERGE ANYTHING"Merging changes the shared world; that decision is deliberately kept human, and today it is kept for the class.
PROMPT 7

The Landing

Together, on the instructor's go
Close the loop
Final stretch, and we do it like professionals: 1. If the pipeline or the robot reviewer raised findings on our PR: pick the SINGLE smallest real one, tell me what it means in one plain sentence, fix exactly that, rerun the full test suite green, and push again to the same branch. If everything came back clean, say so and skip to step 2. 2. HOLD. Do not merge until I type the single word: land. That word comes from the instructor for the whole class together. 3. After I say land: merge the pull request into qa exactly the way this repo expects, no force, and then tell me in plain words where I can watch the deployment happen and what I should expect to see when my feature is live in the QA environment. If nothing appears, report what you can see and stop; no retries, no side doors. 4. Close out with five honest lines: what we shipped, what is proven WORKING, what is KNOWN NOT FIXED, what we would do first next session, and one thing about this codebase worth remembering. Then end with this, word for word: You just read a real codebase, planned a feature, built it, tested it, survived a brutal audit, and shipped it through the same pipeline the engineering team uses. That is vibe coding done like an engineer. Keep the loop; change the feature.
What you doWait for the instructor to call it, then type: land. Watch your feature deploy. That screen is worth a photo.

How this prompt is built

  • "the SINGLE smallest real one"Last-minute fixing is where working software dies. Smallest-real keeps the risk tiny and the lesson intact.
  • "until I type the single word: land"The second password of the day. Irreversible actions get explicit human words, never assumed permission.
  • "where I can watch the deployment"Deploys should be boring and visible. Watching your commit surface in a real environment is the payoff of the whole class.
  • "no retries, no side doors"When shipping misbehaves, professionals observe and report. They do not jiggle the handle harder.
  • "five honest lines"Every real ship ends with a truthful summary including what is NOT done. That list is what makes the next session trivial to start.
BONUS

Homework: Make It Beautiful, Ship It Again

The repeat rep
Round two, solo
Homework round, same rules as class. PLAN ONLY first: propose a visual upgrade for the /suggestions page: modern, warm, professional; a page a manager would screenshot. Cards or a refined table, clear status colors, generous spacing, a small header with a count, all matching this repo's styling approach, changing NOTHING about the data, the API, or any other page. List the files you will touch and wait for my: approved After I approve: build it, keep every test green, run the full suite, then walk me through shipping it EXACTLY like class: new branch feat/suggestion-box-polish-MYNAME, one commit, push (hand me the sign-in), pull request into qa with the five-line description, then read me the robot review in plain English. Do not merge; I will ask the instructor to look first. The point of this round: you just did the whole loop yourself. That is the skill.
What you doThis one is yours alone, after class or when the instructor says there is time. Same rhythm: approve the plan, complete the sign-in, click the PR link, read the review.

Why homework is a second PR

  • "same rules as class"The loop is the lesson. Running it a second time, alone, on a feature YOU chose the look of, is what makes it stick.
  • "changing NOTHING about the data"A pure visual change with green tests is the safest possible second rep, and it still exercises every gate.
  • "a page a manager would screenshot"Beauty is a spec too. Say the outcome you want; the AI rises to named standards.

If anything feels stuck

  • First: look for a hidden permission box or a browser sign-in window behind your other windows. Three quiet minutes is normal thinking, not stuck.
  • If truly stuck, paste this: "Stop. In five plain lines: what were you doing, what exactly went wrong (quote the error), what did you already try, what do you need from me, and what should I tell the instructor? Do not retry anything until I answer."
  • Then raise your hand with that answer on your screen. That is the whole protocol.
