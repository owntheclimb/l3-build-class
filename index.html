Ship Real Software

Today runs on seven prompts, nine pastes in all, each one called out loud in order. You copy each one, paste it, and watch Claude do the engineering, and at two big moments the room decides together when to move. The panel beside each prompt explains how it was built, so after class you can write prompts like these for your own projects.

Get set up (three minutes, follow exactly)

  1. Log into your playground (the virtual computer) the same way you did last session. If you cannot get in, tell the instructor right away and watch the shared screen while it gets sorted; getting you in is the instructor's job. (If your setup runs directly on your own work computer instead of a remote playground, simply skip this step; everything else today is identical.)
  2. Inside the playground, open the Herd app (Start menu, type Herd) and wait until its services show green. Herd is the engine that serves your app; playgrounds that restarted turned it off, and without it your app page says "can't reach this page".
  3. Now open the Claude app. At the top left, click Code.
  4. Next to the word projects click the + sign. A folder window opens. Go to your Herd folder and pick the folder named playground-l3-yourname (the one with YOUR name; the letter after playground is a lowercase L). Click Select Folder.
CHECK: the top of the window now shows playground-l3-yourname. If it shows anything else, or you cannot find the folder, tell the instructor now, before pasting anything. A couple of setups from last session still need a two-minute finish, and that is completely expected.
CHECK: at the bottom right of the message box it should say Opus. If it says something else, click it and choose Opus.
CHECK: find the permission control under the message box and set it to auto approve (it may be labeled Auto, Auto approve, or Accept edits). Without it, Claude stops and waits for a click at almost every step, and your screen looks like it is thinking when it is really waiting for you.
  1. If Claude asks permission to read or edit files in this folder, say yes. If a Windows admin box ever pops up asking to make changes to the computer, the answer is No.
  2. One prompt at a time, in order, and let Claude finish before you paste the next one. You never need to type your own words into the chat today; every word you send lives in a copy box on this page. While Claude works, read what it says out loud in your head; that running commentary is half the class.
  3. If a sign-in window pops up inside the playground at any point, click your own account, let it finish, and come back. That is normal and it will happen at least once.

How this prompt is built

  • "WHY WE ARE HERE..."Every strong prompt opens with context. When Claude knows what is happening, why it matters, and what a good outcome looks like, it makes better decisions for the whole session.
  • "YOU ARE: a senior Laravel engineer"Giving the AI a role tells it which habits to use. A senior engineer reads the code before changing anything and respects the rules of the house, so that is who we ask Claude to be.
  • "at most 14 SHORT lines... plain language"A limit keeps the answer readable. Without one, you would get a wall of text that nobody in the room has time to read.
  • "mark them OFF LIMITS"You set the boundaries before any work exists, and Claude carries those boundaries for the rest of the session.
  • "say NOT FOUND instead of guessing"This is the honesty rule. An AI that is allowed to say it does not know stops inventing answers.
  • "THE FIX-IT-YOURSELF RULE"When something breaks, Claude diagnoses it and repairs it on its own, using everything this briefing taught it about the machine it is standing on. It only hands you a sentence when the fix truly needs a human, like a sign-in window or the instructor.
  • "THE CHECKPOINT RULE"Every prompt you paste quietly finishes or repairs whatever the last step left behind before starting its own work. This is how the whole room ends up in the same place, even when different machines take different little detours.
PROMPT 2

The Plan: My Work Portal

Your first decision
Plan first, build later
Today we build MY WORK PORTAL: a personal task board that lives in this app FOR REAL. The tasks sit in the database, the page talks to a real API, and everything you change is still there after a refresh. That difference, a page backed by a server, is the whole point of today. PLAN ONLY. Do not create or change any file yet. The feature, exactly: - Database table portal_tasks_MYNAME, where MYNAME is the name part of this repo folder (the piece after playground-l3-). The suffix is not optional: every playground in this class shares ONE dev database, so a bare portal_tasks would collide with fourteen classmates. Columns: id, title (text max 120), category (short word), status (waiting, doing, or done; default waiting), status_since (date), owner (a first name), due (date, optional), priority (1 to 3, default 2), notes (longer text, optional), timestamps. - The PortalTask model and a factory. - A seeder adding 8 realistic SAMPLE tasks for an operations person, invented names only, a mix of statuses, dues, and priorities, wired into this repo's normal seeding. - The API, registered so the page's JavaScript can call it with nobody logged in (your required check c below decides exactly how): GET /api/portal-tasks (all tasks, newest first, paged, and the page size is clamped to between 1 and 100 no matter what the request asks for, so a zero, negative, or giant number can never make this public list return everything), POST /api/portal-tasks (create with title, category, optional due and priority), PATCH /api/portal-tasks/{id} (update status, due, or notes; when status changes, set status_since to today). - A page at /my-portal: ONE standalone full page that does NOT extend the app's layout; all styles and script inline; no packages, no build step, no external files. The look, exactly: warm ivory background (#FAF7F2); one huge serif number at the top showing how many tasks are not done, with a small-caps label under it; three columns titled Waiting, Doing, Done; white cards with soft shadows showing title, category as a small tinted chip, owner, due date (amber when overdue), priority as one to three small dots; an add box at the top (title + category, Enter adds it as waiting through the API); clicking a card's circle marks it done through the API (strikethrough, moves to Done); a Defer button on non-done cards pushes due to tomorrow through the API. Every change saves through the API, so a refresh brings back exactly what you left. - Feature tests covering the three endpoints and the page. Also confirm in the plan, from your recon. These are four REQUIRED CHECKS and the plan must answer each in writing: (a) that /my-portal and /api/portal-tasks are unused anywhere in this repo; (b) whether routes/web.php ends in a catch-all or fallback route that would swallow /my-portal; if it does, the plan must say our route is registered ABOVE it; (c) whether the vendor package that ships this template adds CSRF protection to the api middleware group. It very likely does, which means a plain fetch POST from our page comes back 419; if so, the plan must say we print a CSRF token in the page head and send it as a header on every write. The plan may NOT propose editing any middleware, CSRF exception list, or security file to get around this; (d) say back the exact table name you will create, with MYNAME filled in from this repo folder, and confirm the model points at that table while the routes stay exactly /api/portal-tasks and the page stays /my-portal. The database is shared with the whole class; the table name is what keeps everyone in their own lane. Give me the plan in exactly this shape, short lines, plain words: FILES I WILL CREATE, one line each on what it is for. FILES I WILL TOUCH, one line each on the single line I am adding and why. TESTS I WILL WRITE, named, one line each on what it proves. RISKS, the 2 or 3 most likely ways this goes wrong in THIS repo. OUT OF SCOPE, always: login and security files, pipeline files, other tables, installing anything new, and any leftover setup files from earlier sessions (they stay exactly where they are, untouched). Then STOP and wait. Do not build anything until my next message begins with the word: approved. That message will also carry the build instructions.
What you doRead the plan like a boss reading a proposal. If it matches what we said, copy Prompt 3, your approval rides on its first word. If something looks off, raise your hand.

How this prompt is built

  • "PLAN ONLY. Do not create or change"This is the biggest quality trick in AI coding: make the AI think before it types. A mistake in a plan costs nothing to fix, while a mistake in code can cost the whole afternoon.
  • "The feature, exactly:"We spell out the exact shape of the feature so that everyone in the room builds the same thing. A vague wish would produce fifteen different apps.
  • "in exactly this shape"A structured plan can be checked in about a minute. When a plan is one long paragraph, the missing pieces hide inside it.
  • "OUT OF SCOPE, always"Writing down what we will not touch protects us far better than hoping the AI stays away from it on its own.
  • "until my next message begins with: approved"The word approved works like a password for permission, and it keeps you the decision-maker. The password sits on the first line of Prompt 3, so pasting the next prompt is how you say yes.

How this prompt is built

PROMPT 4

The Tests

The gate is real
Earn the pipeline's respect
Here is a fact about this company's platform: when code is submitted, an automatic pipeline runs the tests and REFUSES code that is not properly covered by them. Tests are not homework here; they are the toll gate. So: Write tests, using this repo's own testing style and tools, that prove: 1. GET /api/portal-tasks answers correctly with our seeded tasks, newest first. 2. POST creates a task that then appears in the list, and PATCH really changes status (and sets status_since to today). 3. The /my-portal page loads and shows a seeded task's title. And because happy tests lie, add EVIL TWINS: GET with a completely EMPTY table (still answers politely with an empty list, no crash); a title at exactly the 120 length limit; a PATCH aimed at a task id that does not exist (a polite not-found, never a crash); a request using a method the routes should refuse; and a request asking for a negative or zero page size (per_page=-1), which must still get the normal capped page back, never every row. Then run this repo's own test command against OUR tests plus the suite directory they live in, and report plainly: how many passed, how many failed, how long it took. The full repository suite is the pipeline's job, and we will watch it do exactly that job in a few minutes. If anything fails, fix OUR code or OUR tests and run again until green, telling me each fix in one line. Never weaken or delete an existing test to get green; if an old test fails for reasons unrelated to us, label it PRE-EXISTING, leave that test alone, and note it in one plain line so I can report it to the platform team; we own what we find even when it is not ours to touch. The standing rules from Prompt 1 apply. End with: Ready for Prompt 5.
What you doWatch the test numbers climb toward green. Claude fixes its own failures along the way, and if a fix ever truly needs a human, it will hand you one plain sentence for the instructor.

How this prompt is built

  • "the pipeline... REFUSES code"We tell Claude what happens to weak work here: the company pipeline refuses code that is not tested well enough. Knowing a machine will judge the tests makes Claude write better ones.
  • "this repo's own testing style and tools"Generic tests might not even run in this codebase, so we ask Claude to use the testing tools this repo already uses on itself.
  • "EVIL TWIN"Every test that proves the feature works gets a twin that tries to break it: an empty list, a title at the exact length limit, a request through the wrong door. Real bugs live in those corners.
  • "OUR tests plus the suite directory they live in"Running our own tests locally keeps the loop fast. The company pipeline runs the entire repository suite on the pull request a few minutes later, and that is the honest full check, done by the machine whose job it is.
  • "Never weaken or delete an existing test"Deleting a failing test is the most tempting shortcut an AI can take, so we ban it by name, out loud.
PROMPT 5

The Anti-Prompt

The signature move
Part one, the brutal audit
Change hats completely. You are now a brutal principal engineer reviewing this feature before it may ship, and your reputation depends on catching what is wrong with it. Audit ONLY what we built today. Score it 0 to 100, starting at 0, giving points only for what is proven solid. Hunt, in this order: real bugs (wrong data, wrong order, missed edge cases); places where our code does not match this repo's own style and typing standards; data safety (anything that looks like real names or company data, anything touching tables that are not ours); test gaps (what could break tomorrow with no alarm ringing); and the page itself (anything sloppy). RULES: LIST ONLY, no fixing. Numbered findings, most serious first, one plain-language line each on WHY it matters. No compliments, no filler. A clean category gets the single word CLEAN. Then STOP and wait. Do not fix anything until my next message.
Part two, paste after the room hears the results
Fix EVERY real finding on your list, starting with the most dangerous and working down. One at a time: tell me in one plain line what you are fixing and why it matters, then fix it, and keep going until the list is done. Stay inside today's feature files. If a finding lives in code that is not ours (someone else's tests, the template, the platform), do not touch it; label it FOR THE PLATFORM TEAM and I will pass it along. Never weaken or delete a test to make a problem disappear. When the list is done, rerun the tests the same way Prompt 4 did, show them green, and give me the honest final tally: what you fixed, and anything labeled FOR THE PLATFORM TEAM. End with: Ready for Prompt 6.
What you doRead the list while the instructor walks one audit out loud for the room. Then paste part two and watch Claude work through every real problem on its own list, one plain line at a time.

How this prompt is built

  • "Change hats completely"The brain that built something will defend it. Giving Claude a completely new role with the opposite goal is how you find what the builder skipped. This is the anti-prompt, and it may be the most useful prompt you learn today.
  • "starting at 0"Starting the score at zero changes the psychology. The reviewer has to find reasons to award points instead of finding excuses to wave the work through.
  • "LIST ONLY, no fixing"Finding problems and fixing problems are kept as two separate steps, because doing both in one breath turns into chaos.
  • "Fix EVERY real finding on your list"We never build on top of known problems. Fixing everything now, while the feature is an hour old and fresh in Claude's head, is the cheapest that fixing will ever be. A bug left behind today costs far more to dig out later.
  • "FOR THE PLATFORM TEAM"Some findings live in code that is not ours to touch today. Naming them honestly and passing them to their real owners is how professionals handle a problem that is real but belongs to someone else.

How this prompt is built

  • "the way this company's engineers do"At this point the class stops being an exercise. Your work goes through the same branches, the same pipeline, and the same robot reviewer that this company's engineers face every day.
  • "tell me to complete it and WAIT for me"Sign-in windows belong to humans. Claude is taught to hand them to you and wait, which prevents the silent hang, the single most confusing failure a beginner can hit.
  • "five short lines: WHAT, WHY, HOW TESTED, RISK, ROLLBACK"This five-line description is what makes a reviewer trust a submission. Thinking about how you would undo a change before you merge it is a habit of senior engineers.
  • "translate every finding into plain English"Robot reviews arrive written for engineers. Asking Claude to translate each finding into plain English means you can read them without fear.
  • "DO NOT MERGE ANYTHING"Merging changes the shared codebase that everyone works in, so that decision stays with humans. Today the whole class makes it together.
PROMPT 7

The Landing

Together, on the instructor's go
Close the loop
Final stretch, and we do it like professionals: 1. First, get the PR's current state. Read it yourself from this machine if you can; the company Git server usually answers the same sign-in your push used. If you cannot reach it, ask me for a screenshot: I press Win+Shift+S, drag a box over the PR page, and paste the picture here (a select-all copy of the page works too). 2. If the pipeline or the robot reviewer raised findings on our PR: go through every real one, smallest first. For each, tell me what it means in one plain sentence, fix it, and keep the tests green. If a finding points at code that is not ours from today, label it FOR THE PLATFORM TEAM instead of touching it. When everything real is fixed, push again to the same branch. If everything came back clean in the first place, say so. 3. HOLD, and say plainly that you are holding for the landing word. Do not merge, do not push anything new, and do not touch the PR again until my next message begins with the word: land. That word comes from the instructor for the whole class together.
The landing word, paste only when the instructor calls it
land. Now merge the pull request into qa exactly the way this repo expects, no force, no side doors. What you doWait for the instructor to call it, then paste the landing word above. Watch your feature deploy. That screen is worth a photo.

How this prompt is built

  • "go through every real one, smallest first"The robot's findings are expert advice arriving at the cheapest possible moment to act on it. We clear every real one before landing, so what we ship carries no known problems into the shared codebase. Going smallest-first keeps each fix easy to check.
  • "until my next message begins with: land"This is the second password of the day, and it gets pasted from its own box rather than typed from memory. An action you cannot undo deserves an explicit human word, every single time.
  • "where I can watch the deployment"A good deploy is boring and visible. Watching your own commit appear in a real company environment is the payoff of the whole class.
  • "no retries, no side doors"When shipping misbehaves, a professional stops, observes, and reports what happened. We do not let Claude keep pushing buttons and hoping.
  • "five honest lines"Every real ship ends with a truthful summary, including what is not done yet. That honest list is what makes the next session easy to start.
